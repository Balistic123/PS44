Why OOM ≠ dead end

OOM means the process ran out of memory. It does not mean:

  • no UAF happened underneath
  • no heap corruption occurred before the kill
  • the leak isn't caused by broken object lifetimes (often UAF-adjacent)
  • you can't groom the heap and trigger once per session

We called it a dead end too early. We haven't tried to control anything yet.

What "control" actually means — in order

  1. Prove corruption — sprayed buffers change, weird FontFace state, crash at non-OOM fault
  2. Info leak — read a pointer you shouldn't have
  3. addrof — leak address of a JS object
  4. fakeobj / arbitrary R/W — corrupt TypedArray header
  5. ROP/JOP — native code in WebKit process
  6. Kernel — separate problem for 13.50

We're at step 0→1. OOM on refresh is a constraint, not a verdict.

Strategy given OOM-on-refresh

  • One trigger per browser session — quit browser fully between attempts
  • Heap spray before AND after trigger — catch freed FontFace slots
  • Don't refresh — single page load only
  • Vary spray size/count — match suspected FontFace/CSSFontFace allocation size
  • Delay work post-trigger — corruption may appear async after font loader timer
